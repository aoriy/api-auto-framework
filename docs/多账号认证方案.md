# 多账号会话认证方案

面向「一个工作流里不同接口由不同账号执行」的场景：认证以 **会话 Cookie 为主**，
`Authorization: Bearer` 仅保留一个可选入口。

---

## 零、先厘清两个概念

| | 角色（role） | **账号（account）** |
|---|---|---|
| 是什么 | 业务权限类别（buyer / admin） | 一个具体身份 = 一套凭据 + 一次会话 |
| 是否登录单位 | 否 | **是**，索引维度也是它 |
| 能否有多个 | — | **能**，同角色可有 buyer_a / buyer_b |
| 换它意味着什么 | 换一个请求头就够 | **必须换 CookieJar（即换 `requests.Session`）** |

这条区别就是整套方案的出发点：
**角色差异可以靠请求头表达，账号差异不行——Cookie 是绑在 Session 上的。**

原来的 `roles.yaml` 语义上其实是账号表，现在正式拆开：
账号是索引维度，角色降级为账号的一个属性字段。

---

## 一、总体结构：账号 → 会话 → 请求

```
accounts.yaml（账号表）
      │  一个账号 = 凭据引用 + 怎么登录 + 怎么带鉴权
      ▼
SessionFactory.client(account)        ← 唯一拼装点，账号在此与鉴权策略绑定
      │
      ├── account=buyer_a  → HttpClient#1 → requests.Session#1 → CookieJar#1
      ├── account=buyer_b  → HttpClient#2 → requests.Session#2 → CookieJar#2
      └── account=ops_admin→ HttpClient#3 → requests.Session#3 → CookieJar#3
                                                │
                                         每个请求自动携带本 Jar 的 Cookie
                                                ▼
                                          被测服务（session 表）
```

**三条铁律：**

1. **一个账号一个 `HttpClient`，一个 `HttpClient` 一个 `requests.Session`。**
   CookieJar 挂在 Session 上，实例不共享 → Cookie 不可能串。
2. **登录必须发生在该账号自己的 Session 上。**
   用 `client.request(..., auth=False)` 发登录请求，`Set-Cookie` 才会落进正确的 Jar。
3. **作废会话只作废本人。**
   401 重登只清当前账号的 Session 与缓存，其他账号不受影响。

代码落点：`core/session_factory.py`（全部三条）、`core/http_client.py`（每实例一个 Session）。

## 二、凭证存储：三层，各有各的入口和生命周期

| 层 | 存什么 | 存在哪 | 生命周期 | 谁能读到 |
|---|---|---|---|---|
| **① 静态凭据** | 账号密码、client_secret | `config/secrets.env`（gitignore）/ CI Secret 环境变量 | 长期，人工轮换 | 只有 `SessionFactory._do_login()` |
| **② 会话状态** | CookieJar（SESSION / csrftoken） | **内存**，每个账号一个 `requests.Session` | 进程内；服务端可随时失效 | 该账号自己的 `HttpClient` |
| **③ 会话快照** | CookieJar 的键值副本 | `runtime/credentials.<env>.json`（可关） | 跨次运行复用；`assume_ttl` 到期或 401 时重建 | 框架内部，用于下次启动恢复 |

### 关键设计点

- **明文只有一个入口**：`secrets.env` 或 CI 同名环境变量，CI 优先（`os.environ.setdefault`）。
  账号表里只写 `${BUYER_A_PASSWORD}` 这类引用，永远不写明文。
- **会话状态只在内存**：这是"身份"的活体，不落盘也不出进程。
- **落盘是可选的复用手段，不是可信来源**：删掉 `runtime/` 照样能跑（会重新登录）。
  会话落盘等于**明文会话落盘**，共享机器/生产建议关掉：

  ```yaml
  # config/env/<env>.yaml
  persist_credentials: false
  ```

- **过期怎么判断**：Cookie 的过期由服务端 `Set-Cookie` 决定，客户端拿不到 `expires_in`。
  所以本地给一个保守的 `assume_ttl`（示例里 1800s），**真实失效一律靠 401 兜底重登**。

### 登录时到底发生了什么

```
_do_login(account, spec, strategy)
  ├─ client = self.client(account)            # 取该账号专属客户端
  ├─ strategy.clear_session(client.session)   # 先清掉旧会话，避免残留
  ├─ client.request(method, path, auth=False) # ★ 走该账号自己的 Session
  │      └─ 服务端 Set-Cookie: SESSION=...; csrftoken=...
  │         落进 client.session.cookies        ← 正确的 Jar
  ├─ strategy.snapshot(client.session)         # 抓会话快照
  └─ store.set(Token(account, cookies={...}))  # 按 (env, account) 落库
```

`auth=False` 这一步很关键：它让登录请求本身不注入鉴权，因此不会
「登录需要 token、token 需要登录」死循环；同时又保留了 Session，
所以 `Set-Cookie` 有地方可落。

## 三、请求间的账号隔离

### 请求发出前的装配顺序

```
HttpClient.request(method, path, ...)
  ├─ credential_provider()          # 确保本账号凭证就绪（懒登录 / 命中缓存）
  ├─ strategy.prepare(session=...)  # ★ 从**本账号** CookieJar 取 csrftoken → X-CSRFToken
  ├─ strategy.apply(...)            # 注入 token 类凭证（cookie 策略为空实现）
  └─ self.session.request(...)      # ★ Cookie 由本账号 Session 自动带
```

隔离由两道保险共同保证：

1. **物理隔离**：Cookie 在 `self.session.cookies` 里，而 `self.session` 属于某个账号的客户端实例。
   A 的客户端拿不到 B 的 Session 对象。
2. **逻辑隔离**：CSRF token 与 session 绑定，框架每次从**当前账号**的 Jar 现取现用，
   不存在"沿用了上一个账号的 CSRF"这种可能。

### 越权与串号的兜底

- 响应对象 `ApiResponse.account` 记录了是哪个账号发的。
  `BaseCase.check()` 会把它打进步骤详情（`account=buyer_a`）。
- **约定：凡身份相关的断言，都顺手校验响应里的标识字段**，例如：

  ```python
  self.check("buyer_a 下单", resp, 201, expect=field("data.buyer", "buyer_a"))
  ```

  这样一旦串号，测试会失败而不是静默通过。

### 反面实证（实测结果）

三个账号共用一个 `requests.Session` 依次登录：

```
用共享 Session 登录 buyer_a  后，Jar 里的 SESSION = sess-9e00b2513...
用共享 Session 登录 buyer_b  后，Jar 里的 SESSION = sess-d0fe6c7c5...
用共享 Session 登录 ops_admin 后，Jar 里的 SESSION = sess-8c0d8c456...
→ 共享 Jar 里永远只剩最后一个账号的会话，前两个身份被静默覆盖
```

之后无论谁发请求，服务端看到的都是最后登录的那个账号。**这就是 Cookie 模式下串号的全部机制**，
而且它不会报错，只会让断言莫名其妙地失败（或更糟：莫名其妙地通过）。

## 四、切换账号的正确姿势与注意事项

### 正确姿势：换实例，不换全局状态

```python
class ShopApi(BaseApi):
    account = "buyer_a"          # 页面类声明默认账号

# 同一个用例里，一个页面类可以有多个账号的实例，互不影响
self.shop_a   = self.api(ShopApi)                       # buyer_a
self.shop_b   = self.api(ShopApi, account="buyer_b")    # buyer_b
self.admin    = self.api(ShopApi, account="ops_admin")  # ops_admin

# 需要临时换账号：返回新实例，不动默认账号
self.shop_a.approve("${order_a}")   # 内部 self.as_account("ops_admin")
```

**没有"先登录再切回"这个步骤**——因为没有任何全局状态需要还原。

### 注意事项清单

| # | 注意事项 | 后果 | 本框架的应对 |
|---|---|---|---|
| 1 | **不要共享 `requests.Session`** | Cookie 互相覆盖 → 串号 | 一账号一 Session，工厂内按账号缓存 |
| 2 | **登录必须在该账号自己的 Session 上完成** | `Set-Cookie` 落进别的 Jar，所有请求变未认证 | `_do_login` 用 `client.request(auth=False)` |
| 3 | **CSRF token 与 session 绑定，换账号必须换 CSRF** | 稳定 403 | `prepare()` 每次从当前账号 Jar 现取 |
| 4 | **Cookie 拿不到 `expires_in`** | 本地过期判断失真 | 保守 `assume_ttl` + 401 兜底重登 |
| 5 | **401 重登只能作废本人** | 一个账号过期把所有账号踢掉，重登风暴 | `_renew` 只清当前账号会话与缓存 |
| 6 | **`as_account()` 必须返回新实例** | 污染默认账号，后续步骤身份错乱 | 返回 `type(self)(ctx, account=...)` |
| 7 | **不要靠请求顺序保证身份** | 乱序执行结果不一致 | 身份挂在对象上，与执行顺序无关 |
| 8 | **会话落盘 = 明文凭据落盘** | 泄露风险 | `persist_credentials: false` 可关；`runtime/` 必须 gitignore |
| 9 | **mock/服务端响应体必须读干净** | keep-alive 连接污染 → 后续请求 400 | 见下方「本次实测踩到的坑」 |
| 10 | **登录后 sessionId 应变化** | 会话固定攻击（session fixation） | 服务端登录即换新 sid；测试可断言 |

### 本次实测踩到的坑（值得单独记）

写会话版 mock 时撞到一个**非常隐蔽的 HTTP 层坑**：

> `BaseHTTPRequestHandler` 在 HTTP/1.1 keep-alive 连接上会**复用同一个 handler 实例**
> 处理多个请求。若在鉴权失败时直接返回而**没读走请求体**，残留字节会被当作
> 下一个请求的请求行 → 同一连接上后续请求全部 400。
> 更麻烦的是，若为了避免前者而给请求体加缓存，缓存又会**跨请求残留**，
> 导致第二个 POST 读到第一个 POST 的 body。

修法是：每个请求进入时先 `_read_body(reset=True)` —— 既读干净，又重置缓存。

**这条对写测试框架的人同样重要**：如果你们自建 mock/stub 服务，
或者用自定义连接池，很容易踩到同一个坑，症状是"莫名其妙的 400 或身份串了"。

## 五、可选入口：Authorization

整个项目只在账号表里为开放平台保留一个入口：

```yaml
partner_bot:
  role: partner
  auth:
    type: bearer
    header: Authorization
    prefix: "Bearer "
    token_path: data.access_token
```

页面类写法与 cookie 账号**完全一致**，用例也无感：

```python
class PartnerApi(BaseApi):
    account = "partner_bot"
    def ping(self):
        return self.get("/partner/ping")
```

实测确认：Bearer 通道**不产生任何会话 Cookie**（`ctx.cookies("partner_bot")` 为空），
两条鉴权路径彻底互不干扰。
