2.1 各层职责与禁止事项

层职责只允许 import明确禁止
runner 命令行解析、依赖装配（Settings → TokenStore → SessionFactory → Context）、按套件顺序跑用例、写 JSON 报告、定退出码 全部下层 + yaml 不写业务断言；不直接发 HTTP
cases 组织业务流程步骤、记录每步成败、跨步骤传递变量 apis / core 不拼 URL；不碰凭证；不 import requests
apis 声明式描述「这个页面用哪个账号、哪个前缀、有哪些接口」 core.context（仅此一个） 方法体禁止出现任何凭证代码；不写断言；不处理重试
core 请求出口、账号隔离、凭证生命周期、鉴权策略、响应封装、断言库、异常体系、日志 标准库 + requests + 自身 不 import apis/cases/runner（否则形成环）
config 把 yaml / 环境变量 / 密钥文件收敛成一个不可变的 Settings 与账号字典 标准库 + yaml + core.exceptions 不 import core 的其余部分；不含业务逻辑
三条结构性设计，是这套框架最值钱的地方：
  1. 请求出口唯一 —— 所有 HTTP 都走 HttpClient.request()。页面类不碰鉴权、不碰 base_url、不碰重试。换 httpx/aiohttp 只需改 core/http_client.py 一个文件。
  2. 隔离靠物理而非约定 —— 一个账号 = 一个 HttpClient = 一个 requests.Session，CookieJar 挂在 Session 上且实例不共享，所以「Cookie 不可能串」是结构保证，不是纪律要求。
  3. 鉴权是策略族不是 if-else —— 7 种 auth.type 由 @register 注册进 registry，接真实接口时新增鉴权方式不用改任何既有代码。

3 · 类图

3.1 内核与鉴权类

核心是「一条工厂链」：Context 持有 SessionFactory，SessionFactory 组合出每个账号专属的 HttpClient， HttpClient 再聚合一个 AuthStrategy。注意 Context 只是传参总线—— 它不保存任何账号状态，账号凭证全部托管在 SessionFactory 与 TokenStore，所以切账号不会产生全局状态污染。

6 · 一次接口调用的完整执行时序

runner/main.py :: main()
 ├─ load_settings(env)                  → Settings（含 base_url / api_prefix / retries）
 ├─ load_accounts(accounts_file)        → dict（账号 → {auth, login, ...}）
 ├─ TokenStore(credential_cache)        → 进程内凭证仓库（+ 可选落盘）
 ├─ SessionFactory(settings, accounts, store)
 ├─ factory.login(预登录账号)            ← 可选，--fresh-token 会先 store.clear()
 │   └─ client(account)
 │       ├─ build_strategy(spec["auth"])        ← registry 里按 auth.type 取类
 │       └─ HttpClient(...).bind_auth(策略, token_provider, on_unauthorized)
 ├─ Context(factory, env)               → 传参总线，不持账号状态
 ├─ load_suite(name) / resolve_cases()  → suites/<name>.yaml
 └─ for case_cls in pairs: case_cls(ctx).run()
     ├─ setup_case()
     ├─ for name in step_names():      ← 方法名字典序，不是代码顺序
     │   └─ getattr(self, name)()
     │       ├─ self.api(XxxPageApi)   → BaseApi.__init__
     │       │   ├─ principal = account or role
     │       │   ├─ prefix = ctx.api_prefix（类未声明时）
     │       │   └─ client = ctx.client(principal)   ← 已鉴权，页面类看不到凭证
     │       ├─ api.some_method(...)
     │       │   └─ BaseApi._url(path) → 前缀拼接
     │       │       └─ HttpClient.request()
     │       │           ├─ _join(path)               base_url + path
     │       │           ├─ token_provider()          懒登录，命中缓存≈零成本
     │       │           ├─ strategy.prepare()        补 CSRF 头（CookieAuth）
     │       │           ├─ strategy.apply()          注入 headers/params/cookies
     │       │           ├─ session.request(...)      ← 唯一真正发请求的地方
     │       │           └─ 异常分流：
     │       │               · 网络异常 / 5xx → attempt 重试（retries + backoff）
     │       │               · 401            → auth_retried 标志 → _renew() → 原样重发 1 次
     │       │               · 403            → 不重登，原样返回
     │       └─ self.check(step, resp, expect_status, expect)
     │           └─ CaseResult.steps.append(StepResult)   ← 单步失败不中断
     ├─ teardown_case()                ← 5 个用例全部未覆写（技术债）
     └─ return CaseResult
 ├─ build_report(...)                   → reports/report-<env>-<suite>.json
 └─ exit 0 全通过 / 1 有失败 / 2 框架级错误

P2 core/token_store.py

三条容易反直觉的既有规则（不是 bug，但和大多数人的预期相反，改动前务必先读 BaseApi 的文档字符串）：
  1. 用例步骤按 方法名字典序 执行，不是代码书写顺序 —— 所以必须用 test_01_ / test_02_ 前缀控序。
  2. 页面类自带 prefix = "/xx" 时 不叠加 环境 api_prefix，优先级最高；prefix = "" 表示「path 就是完整路径」。
  3. 收到 403 不做任何自愈 —— 在本项目里 403 语义是「已认证但无权访问」，是 9 处越权断言的测试目标本身；无差别重登会作废一个本来有效的会话并污染证据链。

9 · 建议的后续开发顺序
