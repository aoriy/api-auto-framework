单接口联调手册

api-auto-framework · 单接口联调手册 · 生成于 2026-10-14

适用对象：要给本项目新增/接入接口的人。 目标：让「这一个接口到底通没通」这件事，能在 10 秒内单独问出答案，而不是跑完一整条流程去猜。

0. 结论速览

问题 答案
项目里原本有单接口验证入口吗？ 没有。 调度粒度是「套件 → 用例类」，没有 --case / --only / 单步骤过滤
现在有吗？ 有。 新增 tools/hit.py，一次只打一个接口，打印全链路信息并断言
一个接口要算「真正生效」，看几个点？ 5 个：路由存在 → 鉴权正确 → 契约一致 → 业务规则生效 → 副作用落地（写后必回查）
最容易骗到自己的地方？ 只看 201 Created 就收工。必须再 GET 回来确认

1. 先回答：原来能单独验证一个接口吗？

1.1 runner 的全部调度能力（实测）

python runner/main.py --help 支持的参数只有这些：

参数 作用 能否用来「只跑某一个接口」
--env 选环境（config/env/<env>.yaml） ✗
--suite 选套件（suites/<suite>.yaml） ✗ 粒度是套件
--account / --role 预热指定账号（可重复） ✗ 只影响登录，不筛选执行
--fresh-token 清掉凭证缓存强制重登 ✗
--list-accounts / --list-roles 打印账号表后退出 ✗

而 suites/*.yaml 的结构是：

cases:
  - cases.all_pages_case:AllPagesFlowCase

执行粒度到此为止——没法在里面写「只跑第 3 个步骤」。

1.2 框架内部的粒度边界

cases/base_case.py 的 run() 是这样跑的：

setup_case() → test_01_* → test_02_* → ... → teardown_case()
  • 步骤顺序 = 方法名字典序（所以用 test_01_ 前缀控序）
  • 单个步骤失败不中断后续步骤（这是刻意设计，一次跑完看全貌）
  • 但没有「只执行 test_03_」的开关

所以现状是：「一个用例类」是最小的可执行单元，而一个用例类通常是一条完整业务流程。

1.3 为什么这个缺口很要命

新增接口时典型场景：

申请 → 专家评审 → FAE 汇总 → IPQ 审核 → ...
        ↑ 你要验的是这一环

问题在于：

  1. 上游没通，下游根本没发出去。 你看报告是一排红，但有价值的信号只有最上面那一行，剩下全是「因为没拿到 case_id 所以没发请求」的噪声。
  2. 你要验的接口可能已经好了。 它依赖的上游数据在真实环境里还没造出来，但接口本身完全正常——套件跑不出来这个结论。
  3. 改动影响面看不出来。 你只想确认「我把 path 从 /cases 改成 /flow/cases 对不对」，跑整条流程代价太高。

结论：单接口验证必须单独有入口，不能拿套件凑。 这就是 tools/hit.py 存在的原因。

1.4 补上的东西

tools/
  mock_server.py            dev 环境 mock
  mock_server_session.py    session 环境 mock
  hit.py                    ★ 单接口联调工具（本次新增）

2. 三种单接口测试方式

2.1 方式一：curl / Postman 直打

能用，但不该用于鉴权验证。 本项目的鉴权是 Cookie + CSRF，手工打会踩一串坑：

# 你得自己登录、自己存 Cookie、自己从 Cookie 里抠 csrftoken、自己补 X-CSRFToken 头
curl -c /tmp/c.txt -X POST http://127.0.0.1:18889/auth/login \
     -H 'Content-Type: application/json' \
     -d '{"username":"test1","password":"..."}'
CSRF=$(awk '/csrftoken/{print $7}' /tmp/c.txt)
curl -b /tmp/c.txt -X GET http://127.0.0.1:18889/flow/cases -H "X-CSRFToken: $CSRF"

缺陷清单：

  • 前缀 /flow 要自己拼，拼错了报 404，你会以为是接口不存在
  • CSRF 头漏了会 403，且报错信息不一定告诉你少了什么
  • 没有 401 自动重登（框架里 HttpClient 有，手工打没有）
  • 换账号要重来一遍
  • 无法验证「鉴权体系本身对不对」——因为你绕过它了

结论：curl 只适合确认服务活着（curl http://127.0.0.1:18889/health），不要用它验接口。

2.2 方式二：tools/hit.py（日常主力，推荐）

它复用框架完整装配链路，不是另起一套：

config/env/<env>.yaml ─┐
config/<账号表>.yaml   ─┼─→ SessionFactory ─→ Context ─→ 页面对象 ─→ HttpClient
config/secrets.env     ─┘                                              ↓
                                                   鉴权 / 401自愈 / 重试 / Cookie隔离

也就是说：hit.py 打通 = 用例里也会通（同一份代码路径、同一份凭证缓存）。这是它比 curl 强的根本原因。

2.3 方式三：单条目 suite（进 CI / 要留报告时用）

需要一个能沉淀成报告的「单接口用例」时，新建一个只有一个用例类的套件：

# suites/probe_apply.yaml
name: 申请页单接口探针
description: 只读验证申请列表接口是否可用（安全，无副作用）
cases:
  - cases.all_pages_case:AllPagesFlowCase

python runner/main.py --env session --suite probe_apply
# 报告落在 reports/report-session-probe_apply.json

能力边界：它仍然是「用例类」粒度。要真正做到单接口，得写一个只有一个 test_01_ 方法的小用例类。适合长期值守的场景（比如 CI 里每分钟探一次关键接口）。

2.4 怎么选

场景 用哪个
确认服务活着 curl /health
新增/改动一个接口，我要立刻知道通没通 hit.py
换账号验权限（越权/漏权） hit.py（--account）
验证未登录拦截 hit.py（--no-auth）
接口还没写成页面方法，先探路 hit.py（--raw）
要留给 CI、要出报告 单条目 suite + 小用例类

3. hit.py 使用手册

3.1 参数总表

参数 说明
--env 环境名，对应 config/env/<env>.yaml，默认 dev
--list 打印所有页面类与接口方法后退出（先跑这个）
--list-accounts 打印账号注册表后退出
--api 类.方法 要调的接口，如 ApplyPageApi.list_applications
--account 指定账号，覆盖页面类默认账号
--arg 位置参数（可重复，能当 JSON 解就当 JSON）
--kw 关键字参数 key=value（可重复）
--raw METHOD PATH 不经页面对象，直接打裸路径
--prefix 配 --raw，拼在路径前的公共前缀
--params / --json / --data --raw 的 query / JSON body / 表单体
--header 附加请求头 key:value（可重复）
--no-auth 全新匿名连接发送（见 §6.1，不是简单的 auth=False）
--expect-status 期望状态码，不符即失败
--expect PATH 断言响应体某路径存在且非空（可重复）
--expect-eq PATH=VALUE 断言响应体某路径等于期望值（可重复）
--repeat N 重复发送 N 次，用于观察缓存/幂等
--save PATH 把响应（含完整 headers）存成 JSON，便于照着写页面对象
--max-body 响应体打印上限字符数，默认 2000，0 为不截断
--show-cookies 打印响应里的 Set-Cookie
--log-level 覆盖日志级别，调鉴权链路时用 DEBUG

3.2 五个典型场景（均为实测输出）

场景 1 · 先看有什么接口

python tools/hit.py --env session --list

输出（节选）：

环境 session   base_url=http://127.0.0.1:18889   api_prefix=/flow

ApplyPageApi   默认账号=test1   前缀=/flow
    GET    /flow/cases
           list_applications(status=None, page=1, size=20)
    POST   /flow/cases
           submit_application(title, **extra)

FlowApi   默认账号=test1   前缀=(无)
    POST   /flow/changes
           create_change(title, **extra)
    ...

共 14 个页面类 / 36 个接口方法

它是静态解析源码得出的：HTTP 动词、路径、默认账号、前缀、方法签名一次看全。前缀显示 (无) 表示该类自己声明了 prefix = ""。

清单里带 [辅助] 标记的（如 UserApi.as_public）只换账号、不发请求，不能用本工具直接调。

场景 2 · 打一个接口

python tools/hit.py --env session --api ApplyPageApi.list_applications \
    --account test1 --kw page=1 --expect-status 200

调用 ApplyPageApi.list_applications()  账号=test1  前缀=/flow
  入参: args=[] kwargs={"page": 1}
[list_applications] 请求
  GET http://127.0.0.1:18889/flow/cases
  发起账号 : test1
  query    : {"page": 1, "size": 20}
[list_applications] 响应
  HTTP 200   1.05ms   application/json; charset=utf-8
  body:
    { "code": 0, "data": { "items": [], "total": 0 } }
✅ 通过（1 个响应）  最后一次 HTTP 200

注意它把 最终 URL / query / body / 发起账号 全打出来了——这正是排查「前缀拼歪」「参数没传进去」「用的不是我以为的账号」所需要的信息。

场景 3 · 换账号验权限（最有价值的一招）

同一个接口，两个账号各打一次：

# 创建人 test1 去评审 → 应 403
python tools/hit.py --env session --api FlowApi.sre_review \
    --account test1 --arg CH0001 --expect-status 403

# SRE 专家 test34 去评审 → 应 200
python tools/hit.py --env session --api FlowApi.sre_review \
    --account test34 --arg CH0001 --expect-status 200 --expect-eq data.status=sre_approved

实测输出（前者）：

  POST http://127.0.0.1:18889/flow/changes/CH0001/sre-review
  发起账号 : test1
  HTTP 403   15.6ms
  body:
    {
      "code": 403,
      "message": "account 'test1' (role=creator) is not allowed here",
      "required_roles": ["sre_expert"]
    }
✅ 通过（1 个响应）  最后一次 HTTP 403

「该拒的拒、该放的放」两侧都要测。 只测 403 会漏掉「权限配得太大」；只测 200 会漏掉「权限没收紧」。这套对照就是 §4.2 的权限矩阵。

场景 4 · 验未登录拦截

python tools/hit.py --env session --api FlowApi.me --account test1 --no-auth --expect-status 401

⚠️ --no-auth：使用全新匿名连接（Cookie 与 Token 一个都不带）
  GET http://127.0.0.1:18889/me
  发起账号 : anonymous
  HTTP 401   19.79ms
  body: { "code": 401, "message": "missing or invalid session cookie" }
✅ 通过（1 个响应）  最后一次 HTTP 401

对照（带凭证）：同一条命令去掉 --no-auth → HTTP 200、data.role = creator。两个结果一起才能证明鉴权真的在起作用。

场景 5 · 接口还没封装成页面方法，先裸路径探路

写页面对象之前，先用裸路径摸清真实响应长什么样：

# 路径完全自己说了算：不经过 prefix 逻辑
python tools/hit.py --env session --raw GET /changes --account test1 --prefix /flow
python tools/hit.py --env session --raw POST /changes --account test1 --prefix /flow \
    --json '{"title":"联调验证"}'
python tools/hit.py --env session --raw GET /changes --account test1 --prefix /flow \
    --params '{"page":1}' --header 'X-Trace-Id:abc'

加上 --save 就能把真实响应结构存下来，照着写页面方法：

python tools/hit.py --env session --api ApplyPageApi.list_applications \
    --account test1 --save runtime/probe/apply_list.json

存下来的内容包含 method / url / account / status / elapsed_ms / headers / body / raw_text——写 field() 断言时直接照着 body 的点号路径抄。

3.3 退出码（CI 友好）

码 含义
0 全部断言通过
1 有断言失败（接口通了但行为不对）
2 用法/配置错误（账号不存在、环境不匹配、参数格式错、或框架级错误）

1 和 2 分开很有用：前者是「被测系统有问题」，后者是「你自己的调用姿势有问题」。

3.4 与用例调用同源

环节 hit.py 用例
读环境/前缀 load_settings(env) 同
读账号表 load_accounts(settings.accounts_file) 同
凭证 同一个 TokenStore（同一份 runtime/credentials.<env>.json） 同
会话隔离 同一个 SessionFactory 同
请求出口 同一个 HttpClient（鉴权/401自愈/重试全在） 同
目标方法 同一个页面类的同一个方法 同

所以 hit.py 打通基本等价于用例里会通。 反过来不成立——见 §6.10。

4. 验证点清单：怎么算「真正生效」

4.1 五层判据（缺一层就可能放过 bug）

层 验什么 hit.py 怎么写 常见假绿
① 路由存在 不是 404/405 --expect-status 200（或 201） 404 被当成「接口对但没数据」
② 鉴权正确 该拦的拦、该放的放 --no-auth --expect-status 401；换账号 --expect-status 403 只测登录态，没测未登录/越权
③ 契约一致 字段名、类型、层级 --expect data.id / --expect-eq data.status=sre_approved 只看状态码，字段改名了也不知道
④ 业务规则 状态流转、约束、四眼原则 --expect-eq data.reviewed_by=test34 只看 200，没验规则真的生效
⑤ 副作用落地 写后必回查 先 POST，再 GET 回查 最危险：201 只代表「收到了」，不代表「存下了」

关于第 ⑤ 层（重点）

实测演示：

# 写：提交申请单
python tools/hit.py --env session --api ApplyPageApi.submit_application \
    --account test1 --kw title=单接口联调样例 --expect-status 201 --expect data.id
#   → HTTP 201, data.id = CASE0003

# 回查：确认真的落库了
python tools/hit.py --env session --api ApplyPageApi.list_applications \
    --account test1 --expect data.items
#   → HTTP 200，列表里能看到刚建的单子

为什么必须回查？ 因为 201 Created 只证明服务端接受了请求。写入失败但返回 201、写到了另一个租户、被事务回滚——这些都得靠回查才能发现。

--expect 的语义陷阱

--expect PATH = 存在且非空。所以：

# 这条会「失败」，因为列表是空的 —— 这是刻意的
python tools/hit.py --env session --api ApplyPageApi.list_applications \
    --account test1 --expect data.items
# ❌ 字段 'data.items' 为空值: []

要断言「是个空列表」而不是「有数据」，用 --expect-eq data.total=0，或者干脆只留 --expect-status 200。

4.2 权限矩阵（同一接口 × N 账号）

一个接口的权限写对了没有，用矩阵说话：

API=FlowApi.sre_review; ARG=CH0001
for pair in "test1 403" "test34 200" "test38 200" "test666 403"; do
  set -- $pair
  printf "%-10s 期望 %s  " "$1" "$2"
  python tools/hit.py --env session --api $API --account $1 --arg $ARG \
      --expect-status $2 >/dev/null 2>&1 && echo "✅ 符合" || echo "❌ 不符合"
done

每个接口都该有这张表，写进用例（参考 cases/account_roles_case.py 的做法）。矩阵里最容易漏的是「同级账号也应通过」——比如两个 SRE 专家（test34/test38）权限必须等价。

4.3 会话隔离（凭证不串号）

跨账号操作后，回头确认 A 的会话没被 B 污染：

python tools/hit.py --env session --api FlowApi.me --account test1 --expect-eq data.role=creator
python tools/hit.py --env session --api FlowApi.me --account test34 --expect-eq data.role=sre_expert

ApiResponse.account 字段会记录发起请求的账号名，配合 --expect-eq 就能把串号钉死。

4.4 幂等与重复调用

# 打 3 次，看第 2、3 次是否更快（命中会话缓存）、结果是否一致
python tools/hit.py --env session --api FlowApi.whoami --account test34 --repeat 3

实测：第一次 从缓存恢复会话（2 个 Cookie） 后 4.26ms，第二、三次 0.88ms / 0.71ms。若第 2 次突然变慢或返回不同结果，说明有非预期的会话重建或状态漂移。

4.5 性能基线

python tools/hit.py --env dev --api ProductApi.list --expect-status 200
#   → HTTP 200   25.29ms

响应头里 elapsed_ms 会打印出来。单接口数字落下来，整条流程慢了才知道是哪个环节慢。

5. 新增接口的联调流程（7 步）

以「给申请页面新增一个『撤回申请』接口」为例。

步骤 1 · 探路：确认真实响应长什么样

还没写任何代码，先用裸路径打：

python tools/hit.py --env session --raw POST /cases/CASE0003/withdraw \
    --account test1 --prefix /flow --save runtime/probe/withdraw.json
  • 通过标准：返回 200/201，runtime/probe/withdraw.json 里有真实字段结构
  • 失败长什么样：no route for POST /flow/cases/.../withdraw → 路径记错了，回头核对接口文档
  • 如果这里就不通，别往下走。先和服务端确认路径/方法/参数名

步骤 2 · 定路径与前缀

根据步骤 1 的 URL，判断前缀归属：

情况 页面类怎么写
路径形如 /flow/cases/{id}/withdraw 不写 prefix（继承环境 api_prefix），方法里写 f"/cases/{case_id}/withdraw"
路径形如 /withdraw/{id}（独立顶级路径） 环境 api_prefix 之外，写 prefix = ""，方法里写完整路径
路径形如 /flow-v2/xxx（类自带固定前缀） 写 prefix = "/flow-v2"

这是最容易出错的一步（拼错了就是 404）。决策依据见 §6.3。

步骤 3 · 写页面方法

在 apis/apply_page.py 加一个方法。方法体里不允许出现任何凭证代码：

def withdraw_application(self, case_id, reason="", **extra):
    """撤回申请。"""
    payload = {"reason": reason, **extra}
    return self.post(self.ctx.interpolate(f"/cases/{case_id}/withdraw"),
                     json=self.ctx.interpolate(payload))

约定（照抄现有方法的骨架就行）：

  • 一个接口 = 一个方法，方法名用动词
  • **extra 兜底，方便临时塞参数联调
  • 路径和 payload 都过 self.ctx.interpolate(...)，这样 ${case_id} 这类变量能自动替换
  • 直接 return 响应，不要自己解析、不要自己断言（断言属于用例层）

def test_05_withdraw_application(self):
    page = self.api(ApplyPageApi)                    # 默认账号 test1
    resp = page.withdraw_application(
        self.ctx.get("case_id"), reason="用例内撤回")

6. 注意事项（全部来自实测踩坑）

6.1 --no-auth 为什么不能用 auth=False 实现

HttpClient.request(auth=False) 只跳过「注入鉴权头」这一步。Cookie 是 requests.Session 自动带的——凭证本来就在 Session 的 CookieJar 里，跳过注入带不走它。

实测证据：一开始用 auth=False 实现 --no-auth，打 FlowApi.me 返回的是 200 + data.role=creator，也就是根本没测成未登录。

正确做法：换一条全新的 requests.Session（本工具用 AnonymousContext 直接构造一个未绑定鉴权策略的 HttpClient）。改完实测为 401 missing or invalid session cookie。

推广结论：任何「模拟未登录」的需求，都必须保证请求上真的没有 Cookie，而不是「不主动加头」。

6.2 Git Bash 会改写以 / 开头的参数

MSYS 把 /flow 当路径处理，实际传给 Python 的是：

E:/soft/WorkBuddy/resources/vendor/PortableGit/flow

于是 URL 变成 http://127.0.0.1:18889/E:/.../PortableGit/flow/...，服务端报 no route。看起来像接口不存在，其实是你的参数被 shell 改了。

两种解法：

# 解法 1（推荐给脚本）：关掉路径转换
MSYS_NO_PATHCONV=1 python tools/hit.py --env session --raw GET /changes \
    --account test1 --prefix /flow

# 解法 2：不写前导斜杠，工具会自动补
python tools/hit.py --env session --raw GET changes --account test1 --prefix flow

本工具会自动还原被改写的参数（通过 cygpath -m / 拿到 MSYS 根目录后剥掉）；万一还原不了，会直接报错并提示上面两种解法，而不是让你对着 404 发呆。

6.3 prefix 三态必须分清

最终 URL = base_url + prefix + path，而 prefix 有三种语义：

页面类写法 含义 适用
不写 prefix None → 回落环境配置 api_prefix 默认，绝大多数页面
prefix = "" 明确「无前缀」，方法里的 path 就是完整路径 顶层路径接口（如 FlowApi：/flow/changes）
prefix = "/xx" 类自带固定前缀，优先级最高 独立子系统（如 OrderApi: /orders）

注意页面类前缀不会自动叠加环境前缀——prefix = "/orders" 就是最终前缀，api_prefix: /flow 对它无效。判断方法直接看 hit.py --list 里打印的 URL。

6.4 环境与账号表是耦合的（拿错环境报的是「账号不存在」）

config/env/<env>.yaml 里的 accounts_file 决定读哪张账号表。两个环境用的是不同表：

环境 base_url 账号表 账号
dev 127.0.0.1:18888 config/roles.yaml admin / guest / merchant
session 127.0.0.1:18889 config/accounts.session.yaml test1 / test34 / test38 / test666 / buyer_a / buyer_b / ops_admin / guest_web / partner_bot

后果：8 个 *_page.py 声明的是 session 账号，用 --env dev 打它们会报：

账号 'test1' 不在环境账号表里。
当前可用的账号：admin, guest, merchant
（提示：页面类的默认账号可能属于另一个环境，用 --account 显式指定）

记住这条：看到「账号不存在」，先想是不是环境选错了，而不是去改账号表。

同类问题在套件层也有：python runner/main.py --env session --suite regression 会是 0/2 全红，因为 regression 套件里的用例用的是 dev 账号。这不是 bug，是环境-套件配错了。

6.5 hit.py 不做跨步骤变量传递

${var} 需要 Context 里有值。单接口调用时上下文是空的，所以：

python tools/hit.py --env session --api ShopApi.place_order --account buyer_a \
    --kw product_id='${pid}'
# [框架级错误] FrameworkError: 上下文里没有变量 'pid'，已有变量: []

行为是正确的（早失败、报错点明缺哪个变量），但意味着：有前后依赖的场景不能靠 hit.py 串起来，要用一个临时用例类，或者手工把上一步的真实值填进去（这也是为什么 --save 和回查很重要——你能从响应里拿到真实 id）。

6.6 mock 是有状态的，写接口会留脏数据

tools/mock_server*.py 在内存里维护数据。实测连续调用后：

CASE0003   ← 提交申请单产生
CH0001     ← 创建变更单产生

而这些不会自动清理——项目里 5 个用例全部没有覆写 teardown_case()。真实环境接入前必须先约定清理策略（见 docs/真实接口接入操作指导.md）。

联调期的自保做法：

  • 优先用读接口验证（GET），写接口只在必要时打
  • 打写接口时把产生的 id 记下来（--save 会帮你存）
  • 别在共享环境里跑「批量压测式」的重复写调用

6.7 401 自动重登只对「本来就要凭证」的账号生效

core/http_client.py 里的 401 自愈条件是：

if raw.status_code == 401 and self._strategy.requires_credential:

所以：

  • cookie / bearer / header 账号：收到 401 会作废本人会话并重试一次（这是它该有的行为）
  • none 账号（如 guest）：401 是权限/配置问题，重登没意义，不会重试
  • 只重试一次，避免凭证配错时死循环

联调时看到 401，先确认「这个账号本来就该带凭证吗」，再决定是查凭证还是查权限。

6.8 单接口调通 ≠ 用例通过

单接口验证的上下文是空的，用例里的上下文有前序步骤的产出。两者差异：

差异点 表现
数据依赖 单接口用你手填的 CASE0003（真实存在），用例里要用上一步产出的 case_id
执行顺序 用例步骤按方法名字典序跑，新加的方法名排在哪个位置要算清楚
状态污染 单接口跑 N 次是 N 个独立请求；用例里同一账号同一 Session，前一步的改动会影响后一步
变量替换 用例里 ${var} 有值，单接口里没有

所以步骤 7 的整条套件回归不能省。

6.9 凭证缓存的位置与强制刷新

  • 落盘位置：runtime/credentials.<env>.json
  • 由 TokenStore 托管，用例完全无感知
  • 想强制重新登录：给 hit.py 或 runner 加 --fresh-token
  • 关掉落盘：环境配置里 persist_credentials: false

排查「我明明改了凭据却没生效」时，顺序是：① 环境变量是否覆盖了 secrets.env → ② --fresh-token 重试一次 → ③ 看一眼 runtime/credentials.<env>.json。

6.10 报告里有敏感信息

runner/main.py 会把凭证写入报告：

"preview": (t.value[:8] if t.value else ",".join(sorted(t.cookies))[:32])

即 token 前 8 位或 Cookie 名列表，落在 reports/report-<env>-<suite>.json。接真实环境后：

  • 报告不要外发
  • 共享机器上跑完清理 reports/ 和 runtime/

（reports/、runtime/、config/secrets.env 都已在 .gitignore 里，不会进版本库。）

6.11 联调期间打开 DEBUG 日志

鉴权链路出问题（CSRF 缺失、Cookie 没带上、策略选错）时：

python tools/hit.py --env session --api FlowApi.me --account test1 --log-level DEBUG

会打印策略装配、登录过程、每次响应的摘要（HttpClient._trace）。比盲猜快得多。
