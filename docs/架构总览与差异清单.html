一、架构总览：六层单向依赖

依赖方向严格单向、不可逆：上层能调下层，下层完全不知道上层存在。这是「把 mock 换成真实接口时用例层零改动」的结构基础。左侧五层是主链路，右侧两栏是横切件与产物。

2.2 两套账号域并存（全项目最易踩坑处）

apis/ 下两种页面对象声明的是两张不同账号表里的账号。这不是 bug，但它是「环境与套件隐式耦合」的根因：页面类不校验账号属于当前环境，错误在首次构造页面对象时才暴露。

实测后果：--env session --suite regression 会 0/2 全红 —— 套件用的是 dev 账号表里的账号，而 session 表里没有 merchant/guest 这两个名字。这不是框架 bug，但没有任何预检会提前告诉你。

三、一次请求的完整数据流

从用例到响应共 8 步，其中只有第 3 步与第 6 步涉及鉴权，且这两步都在 HttpClient 内部完成 —— 页面类看到的只是一句 self.post(path, json=...)。

四、鉴权自愈与重试（控制流）

重试有三条独立通路，都收口在 core/http_client.py::request() 的同一个 while True 里：网络异常重试、5xx 重试、401 自愈。前两者共用 attempt 计数，第三者用独立标志 auth_retried。

场景处理依据
网络异常（连接失败/超时）按 settings.retries（默认 2）重试，退避 backoff × attempt 秒http_client.py:115-119
响应 5xx同上，共用 attempthttp_client.py:159-161
响应 401 且账号需凭证作废本人会话 → 重新登录 → 原样重发一次；上限 1 次，由 auth_retried 独立保证http_client.py:130-150
重登后仍是 401不再重试，原样返回 401 + 一条 warning（提示查口令/账号状态/脏缓存）http_client.py:152-157
游客（type: none）收到 401不重登：本来就没带凭证，重登无意义同理 Basic
响应 403不重试、不自愈，直接返回见 §7 规则 R7

五、执行流程：8 阶段线性状态机

业务单据的状态机是强制线性的：每个环节只接受「上一步刚完成」的状态，越阶一律 409。这既是「顺序约束真的被校验」的保证，也是造数无法跳阶、无法并行的根本原因。

八、规则 × 你的预期：一致性对照（核心）

一致 部分偏离 偏离 / 未落地
你的预期框架现状判定差异点与影响
E1 面向页面：一页面类一文件、一接口一方法 R1 完整落地：8 个 *_page.py + 6 个业务域 API，方法名即接口名 一致 无偏离。接真实接口时只改页面类的 path/入参/account，用例层不动（R23）。
E2 以账号为主、角色自动展示 R2/R3：账号为索引维度与登录单位，角色是它的属性字段 部分偏离 ① 「角色自动展示」只在「1 账号 : 1 角色」时成立。当前 12 个账号全部满足，所以看不到问题；一旦出现「一个账号多个角色」：SessionFactory._clients 按账号缓存，无法表达多角色，越权断言会静默失真（比报错危险）；mock 侧账号表若 value 写成 list，直接 TypeError: unhashable type: 'list'。
② 旧名双口径仍在：roles.yaml 顶层用 roles:、BaseApi.role = "guest" 作默认值、as_role()、ctx.available_roles、load_roles、Settings.roles_file 全部保留兼容。
影响：「以账号为主」已经做到，但「角色」在代码里同时是账号别名和权限属性两种含义，阅读与排查时容易误判；dev 表的键名还是 roles:，与 session 表的 accounts: 不统一。
E3 链式调用 登录方法().接口方法() 未实现。现有等价能力：self.api(PageCls, account="x") 与 BaseApi.as_account() 偏离（未采用） ① 结构冲突：链式要求接口方法返回「可继续链式的句柄」，而页面方法返回的是 ApiResponse（数据终结符）。要支持链式得让页面方法回传会话句柄，直接破坏 R1「一接口一方法」的返回语义。
② 语义风险（最需要警惕）：self.login("test1").submit_expert_review() 能跑通且可能全绿 —— 用创建人账号执行了评审动作，绕过四眼隔离。框架的 self.api(P, account=…) 让身份显式，反而更容易被 review 发现。
结论：套件主体维持 A 方案（self.api(P)）+ B 方案（显式换账号）；链式最多留给一次性探针，不要进用例。
E4 鉴权失败自动重登并重试原调用 R14~R18 已实现；本轮另修掉一个计数缺陷（attempt == 1 → 独立 auth_retried） 一致 实现位置 core/http_client.py:130-150，上限严格为每请求 1 次。
唯一偏离：你最初描述的状态码是 403。框架明确不做 403 自愈（R16）—— 本项目 403 承载「已认证但无权访问」，6 处 account_roles_case 越权断言 + order_flow_case test_05 + multi_account test_07/08 都依赖它。
影响：若真实后端用 403 表达「会话失效」，自愈不会触发，用例会直接收到 403 失败。正确做法是让后端把「失效」统一用 401 表达，而不是把框架所有 403 当过期。
E5 凭证没过期就继续复用（不重建会话） R19：TokenStore.get() 命中未过期凭证即复用；_restore() 把落盘 Cookie 灌回 Jar 部分偏离 核心差异：判定「过期」用的是本地假定值，不是服务端真实过期时间。
  • cookie 账号：assume_ttl: 1800（写死 30 分钟，accounts.session.yaml:26），注释自陈「真实过期靠 401 兜底」
  • token 账号：用登录响应的 expires_in，缺失时 default=3600（auth/base.py:94）
  • 另有 30 秒安全边际，is_valid() 提前 30s 判定失效（token_store.py:43-47）
影响：① 服务端会话 < 30 分钟 → 本地误判有效，必先失败一次 401 才兜底（每次起新进程都可能多一次往返）；② 服务端会话 > 30 分钟 → 本地到点即作废，多余重登一次，正好违背「没过期就继续复用」；③ persist_credentials: true 会把整份 CookieJar 明文落盘并跨进程复用，可能复用一个已被服务端作废的会话。
建议：让登录响应返回真实 expires_in（cookie 策略也读），或把 assume_ttl 设成明显小于服务端最短会话时长。
E6 性能造数：对接真实环境（不 mock）、上万笔、每环节只到 FAE 汇总 尚未落地。框架侧存在 3 个硬缺口，见右列 偏离（阻塞） ① 无删除能力（最严重）：BaseApi.delete() 只是管道（base_api.py:78-79），14 个页面类无一暴露删除方法，两个 mock 也只有 GET/POST/PUT，没有 DELETE 路由 → 造完的数据无法通过接口回收，真实环境会留下 1~3 万笔脏单。
② 无环境预检：环境与套件/页面类隐式耦合（§2.2），接真实环境若只改 base_url 不改账号表，报错发生在首次构造页面对象时（RoleNotDefined），而不是启动即失败。
③ 无回收钩子：5 个用例全部没有覆写 teardown_case()（只有 base_case 里的空实现）→ R6 里「teardown 清理数据」这条约定实际形同虚设。
另需注意：报告会把凭证前 8 位写进 JSON（runner/main.py:102），接真实环境后 reports/ 里会出现真实 token 片段；title 是否有唯一约束、环节是否有通知/工单副作用，都必须在真实环境确认后才能开跑。
E7 单接口联调：能单独验证某个接口是否生效 tools/hit.py（571 行）：--list / --api 类.方法 / --raw / --account / --no-auth / --expect* / --save 一致 无偏离。退出码与 R24/R25 一致；手册见 docs/单接口联调手册.md。
E8 重复执行某用例 1 万次并统计成败 tools/repeat_case.py（327 行）：装配链路与 runner 同源，循环内只登录一次，失败原因按「步骤 + 归一化原因」聚合 一致 无偏离。自测：成功路径 50/50（349 次/秒、单次 2.85ms）；失败路径正确聚合且退出码 1。注意每条记录都会真实产业务数据，与 E6 的清理问题是同一个坑。

九、建议处理顺序

  1. 接真实环境前先补删除能力（E6-①）。在页面类按真实接口补 delete_* 方法，或提供「按 title 前缀批量清理」的运维脚本 —— 否则 1 万次重复执行/造数会把真实环境搞脏且不可逆。
  2. 加环境预检（E6-②）。启动时校验「本环境账号表 ⊇ 套件涉及的页面类所声明的 account」，不满足直接退出码 2 并指明缺哪个账号。
  3. 补 teardown_case 覆写（E6-③）。让 R6 的清理约定真正生效。
  4. 收敛凭证落盘（E5-③）。真实环境把 persist_credentials 置 false；报告里的凭证片段改成固定掩码（如 ***）。
  5. 统一角色口径（E2-②）。把 roles.yaml 顶层改成 accounts:，明确 as_role()/ctx.available_roles 等旧名是待移除的兼容层而非并列概念。
  6. 对齐 403 语义（E4）。与后端确认「会话失效」统一返回 401；否则 E4 的自愈在真实环境形同虚设。
  7. 让 cookie 会话拿到真实 TTL（E5）。登录响应返回 expires_in，去掉 assume_ttl 的乐观假设。
