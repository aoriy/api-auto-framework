# 角色切换方案评估 & Cookie vs Authorization 选型

面向"面向页面 + 多角色"接口自动化框架的设计评审记录。

---

## 一、对"先调角色鉴权方法，再调目标接口方法"的评估

### 结论

| 设计要点 | 评价 |
|---|---|
| 一个业务域一个类、一个接口一个方法 | ✅ 正确，页面对象模式的核心价值 |
| 调用时把接口当方法直接调用 | ✅ 正确，业务语义直接表达在用例里 |
| 多角色用不同鉴权方式访问同一批接口 | ✅ 方向正确 |
| **切换角色时先调 `login_as()` 再调接口** | ⚠️ 有隐患，见下 |

问题不在"切换角色"，而在**把角色做成了全局可变状态**。

### 五个潜在问题

| # | 问题 | 后果 |
|---|---|---|
| 1 | 角色状态挂在共享对象 / 全局 session 上 | 用例 A 切了 admin，用例 B 以为自己是 merchant，实际拿着 admin 的 token。执行顺序一变结果就变，产生假绿 / 偶发失败 |
| 2 | "先登录再调用"靠调用者纪律保证 | 漏掉一行，代码照样跑，只是用错身份。这类 bug 在 code review 中极难发现 |
| 3 | 并发不安全 | `pytest-xdist` 或线程池并行跑用例时，共享的角色状态互相覆盖 |
| 4 | token 生命周期泄漏到用例层 | "过期怎么办""401 怎么办""缓存复用怎么做"散落到每个用例的 setup，重复实现 |
| 5 | 同 URL 多角色时语义无法区分 | `/orders` 商户看自己的、admin 看全部；`login_as` 模式只能靠"记得先切"，无法从方法名看出用的是谁 |

### 推荐改法（按侵入性从小到大）

```python
# ① 最小改动：切换只作用在局部变量上，不改任何人
as_admin = user_api.as_role("admin")
as_admin.list_all()

# ② 推荐：角色即依赖，页面类声明默认角色
class OrderApi(BaseApi):
    role = "merchant"
    def admin_stats(self):
        return self.as_role("admin").get("/stats")   # 返回新实例，不污染默认角色

# ③ 想保留显式感：从上下文按角色取客户端
admin = ctx.client("admin")
admin.get("/orders/stats")
```

需要"块级切换"时用上下文管理器，但要认识到：**需要在退出时"还原"，本身就说明还是可变状态**，不如一开始就无状态。

```python
with ctx.as_role("admin") as admin:
    admin.get("/orders/stats")
```

### 三个验收测试

1. **乱序**：把 `suites/*.yaml` 里用例顺序打乱，结果必须完全一致。
2. **并发**：线程池同时跑两个角色的用例，不能互相污染。
3. **故意漏切**：删掉切换那一行，框架必须报错（断言响应里的 `role` 字段），而不是静默通过。

第 3 条最关键。当前框架的 `ApiResponse` 已带 `role`，`check()` 会把 `role=merchant` 打进步骤详情。
**建议再加一条约定：凡是身份相关的断言，都顺手校验响应里的 role。**

## 二、Authorization 与 Cookie 的区别

### 根本差异

一句话：**身份放在服务端还是客户端。**

- **Cookie / Session**：登录后服务端建会话（`sessionId → user`），通过 `Set-Cookie` 下发一个不透明的 ID。
  客户端只持有索引，**身份状态存在服务端**。浏览器自动携带，因此有 CSRF 风险。
- **Authorization: Bearer**：登录返回令牌（JWT 或 opaque）。JWT 自包含签名 + `userId/exp/role`，
  服务端验签即得身份，**不需要查会话存储**。客户端必须**显式**加头，因此天然免疫 CSRF。

### 逐项对比

| 维度 | Cookie / Session | Authorization: Bearer |
|---|---|---|
| 身份存放 | 服务端会话存储（内存 / Redis / DB） | 令牌里（JWT 自包含）；opaque token 仍需落库 |
| 客户端是否要写代码 | 不用，浏览器自动附带 | 要，每次显式加头 |
| CSRF | 有风险，需 `SameSite` / CSRF Token | 基本免疫 |
| XSS | 可防（Cookie 设 `HttpOnly`） | 较弱（`localStorage` 可被 JS 读） |
| 即时吊销 | 容易，删会话立刻失效 | 难，签出后有效到 `exp` |
| 水平扩展 | 需共享会话存储 | 无状态，天然易扩 |
| 单请求体积 | 小（一个 ID） | 大（JWT 常数百字节） |
| 跨域 | 麻烦（CORS 需 credentials 且不能用 `*`） | 简单（就是个头） |
| 移动端 / 小程序 / 第三方 | 不友好 | 友好 |
| 微服务间调用 | 不适合 | 适合 |
| 网关鉴权 | 需查存储 | 验签即得身份，可直读 role |

### 适用场景

**Cookie 更适合**

- 浏览器为唯一入口的传统 Web 应用，前后端同域。
- 对"强制下线、踢人"有硬要求（运营后台、风控系统）。
- 团队不想承担 JWT 密钥轮换 + 刷新令牌 + 黑名单的复杂度。

**Authorization 更适合**

- 有 App / 小程序 / 开放平台等第三方客户端接入。
- 前后端分离、跨域部署。
- 服务拆分后的内部调用（服务间传 Cookie 很别扭）。
- 网关层要做无状态鉴权（JWT 里带 role，验签即拦）。

## 三、结合"以 Cookie 为主"现状的分析

### 先分清是哪一层的事

- **A. 后端就是 session-based**（服务端真的存会话）
  → 测试框架跟着用 Cookie 是**正确**的，`requests.Session` 自动管理 CookieJar，没有争议。
- **B. 后端签的其实是 token，只是塞进 Cookie 传输**
  → 这不是"鉴权方式选择"，只是"传输方式选择"，随时可以额外加 Authorization 头，改造成本很低。

若属于 A，"以 Cookie 为主"合理。出现下列任一信号时，应为 Authorization 留出口：

| 信号 | 建议 |
|---|---|
| 出现 App / 小程序 / 开放平台 | 引入 Authorization |
| 服务拆分、有网关 | 引入 Authorization |
| 前后端分离跨域部署 | 引入 Authorization |
| 需要立刻踢人 / 强制下线 | 必须保留 Cookie / Session |
| 只有浏览器 Web 端且可实现共享存储 | Cookie 为主即可 |

**最稳的是双轨**：Web 端走 Cookie，App / 开放平台走 Bearer，网关统一成内部身份。
测试框架侧不需要改用例——只换 `roles.yaml` 里该角色的 `auth.type`。

### Cookie 模式落到自动化测试上的四个坑

1. **CSRF Token 回填（最常见）**
   纯 Cookie 方案后端通常对写操作（POST/PUT/DELETE）校验 CSRF。测试框架必须先取出
   `csrftoken`（来自登录响应、页面或 cookie），再回填到 `X-CSRFToken` 头，否则下单类接口稳定 403。
   **当前框架缺少这个钩子，是接 Cookie 后端时第一个会撞上的问题。**

2. **拿不到有效期**
   Cookie 的过期由服务端决定，客户端通常拿不到 `expires_in`。`TokenStore` 的 `expires_at`
   在 Cookie 模式下基本失效——解析 `Set-Cookie` 的 `Expires` 属性，或者置 0、完全靠 401 兜底重登。

3. **`requests.Session` 每个角色一个，不能共用**
   Cookie 模式用 `Session` 自动管 CookieJar 最省事，但共用 Session 就等于共用 Cookie，
   直接回到"串号"问题。当前 `SessionFactory` 每个角色一个独立 `HttpClient`、各带一个 `Session`，符合要求。

4. **补一条会话固定检查**
   登录成功后 `sessionId` 应该变化（防 session fixation）。这是 Cookie 方案特有的、值得加的断言。

### 落地代价

接 Cookie 后端不需要重构：

```
core/auth/strategies.py   已内置 @register 的 CookieAuth（type: cookie）
config/roles.yaml         把该角色的 auth.type 改成 cookie
core/http_client.py       可选：补一个「登录后取 CSRF Token 并回填」的钩子
```

用例层与页面对象层**一行都不用动**。这正是策略模式该发挥的作用。
